# audio_ai 异步处理框架（BlockWorker）

这份文档解释 `audio_ai_process` 的异步处理框架：一条音频从设备进来后，哪些工作在
主线程、哪些工作在后台、两边怎么交换数据，以及为什么这样分。读完应该能回答三个
问题：主线程在干什么、后台线程在干什么、结果怎么回到界面。

文档先给一张全景图，再按「每一步在做什么」把流程走一遍；然后解释为什么需要这层
框架、Worker 和业务类各自承担什么；最后用一次完整的唤醒过程和几条关键约定收尾。
代码细节不是重点，理解这套分工和扩展方式才是。

> **代码位置**：`audio_ai_process/block_worker.h`（header-only 模板，随
> `lib_audio_ai_process` 安装）；单模式 Session 在 `asr_session.h/.cpp`。
>
> **状态**：已落地。`test_mic_asr.cpp` 已用 `BlockWorker` + `AsrSession` 替换
> 原来的 `AsrWorker`；双模式入口 `test_mic_kws_asr.cpp` 待实施时复用同一套装配。

## 1. 先看全景：一条音频的完整路径

图中的编号对应后面的逐步说明。实线是音频和特征的流向，右下角那条回线是结果的
流向。

```
① 设备 / wav
      │ 16 kHz PCM16
      ▼
② HkSdkAudioClient / wav_reader
      │ PCM16
      ▼
③ AudioPreprocess（LogFBank）
      │ LogfbankFeatures (n, 80)
      ├────────────────────────────────┐
      ▼                                ▼
④ SpectrogramImage        ⑤ BlockWorker 音频特征输入队列
   （主线程渲染）            （有界，满时丢最旧）
                                         │
                                         ▼
                                  ⑥ 后台线程（唯一）
                                     session.on_block(输入块)
                                         │
                                         ▼
                                  ⑦ 业务 Session
                                     ├ 单模式：AsrSession
                                     └ 双模式：KwsAsrSession
                                         │
                                         ▼
                                  ⑧ 快照（text / mode / 事件）
                                         │
                                         ▼
                                  ⑨ 主线程读快照显示
```

### ① 采集：把声音变成 PCM

设备侧由 `HkSdkAudioClient` 负责登录、启动语音转发、收 G.722.1 编码包并解码成
PCM16；PCM 下行的 32 kHz 数据会在采集库内部降采样到 16 kHz。wav 入口不经过设备，
由 `wav_reader.h` 直接解析 RIFF，取出第一声道。两条路最终给出同一种东西：
**16 kHz、单声道、int16 的 PCM 块**。

这一步属于主线程。它只关心「有没有新音频」，不关心音频之后会被谁识别，也不需要
知道模型的存在。采集库还负责一些设备侧的细节，比如上行保活、断线补零、暂停恢复，
但这些都不影响后面的处理框架。

### ② 前端：把 PCM 变成特征

`AudioPreprocess` 接收任意长度的 PCM 块，做分帧、预加重、加窗、FFT、Mel 滤波和
取 log，输出 `LogfbankFeatures`：一个 `n × 80` 的行主序矩阵，每行是一帧、每列是
一个 Mel 频带。

前端是流式的：这次没凑满一帧的样本留在内部缓存里，下次接着凑。所以每次拿到的
块可能有很多帧，也可能 0 帧；0 帧不代表丢音频，只代表「这一轮还没有新帧」。这个
细节很重要，因为音频特征输入队列会把 0 帧块直接过滤掉，而不会把它当成一次有效的投递。

到这里为止，所有工作都在主线程，而且都很快——真正耗时的模型推理还在后面。

### ③ 分叉：同一份特征，两条去处

一块特征产出后，主线程把它同时交给两个方向。显示方向交给 `SpectrogramImage`，
它维护最近若干帧，把新帧贴到右端，主线程负责画到窗口上；解码方向则把特征块投进
`BlockWorker` 的音频特征输入队列，交给后台线程。

这两个方向是互不等待的。语谱图慢一点，不影响解码；解码慢一点，也不影响取流和
画面。可视化不参与解码，解码也不参与显示，它们只共享同一份特征。这种分叉看起来
简单，但它是「主线程保持实时」的关键：渲染和解码各自有自己的节奏，不会互相拖累。

### ④ 显示：主线程只做渲染

主线程每轮检查有没有新特征，有就更新语谱图，然后处理按键、刷新窗口。它不调用
任何模型，也不等待后台线程。窗口底部的状态文字不在这里算，而是从快照里读，
见第 ⑨ 步。

渲染本身也要花时间，但它和解码是两件独立的事。Jetson 上的实测表明，把推理留在
主循环里会让主循环吞吐掉到 0.99，刚好擦着实时；把推理挪走之后，渲染再重也不会
拖垮取流。

### ⑤ 投递：把音频特征输入块放进有界队列

主线程调用 `worker.push(块)`，把这一块特征放进 **音频特征输入队列**——这是 Worker
内部唯一的那条有界队列，专门承载「喂给音频处理能力的输入」，不是通用的消息队列，
也不承载输出。队列里的一项叫**音频特征输入块**，包含两样东西：前端产出的特征块
（`LogfbankFeatures`），以及一个「是否为收尾块」的标记。后续无论接 ASR、KWS 还是
新的音频能力，输入都统一成这个形状。

投递有三个约定。

第一，**不阻塞**。音频特征输入队列满时丢掉最旧的一块，主线程立刻返回，继续取流。

第二，**0 帧块不入队**。没有新帧的块不占队列容量，也不计入丢弃。

第三，**按值移动**。音频特征输入块进队列后，主线程手里的 `feats` 可以安全地被下一轮
覆盖，不会出现后台还在读、前台已经改写的情况。

「丢最旧」不是因为内存不够——队列总共才几十 KB——而是因为解码落后时，继续囤只会
让显示越来越滞后。丢掉过时的输入，界面才能始终贴近当前声音。丢了多少块会进统计，
用来判断后台是否跟得上。

### ⑥ 后台线程：一次只处理一块

Worker 在构造时启动唯一一个后台线程。这个线程反复做一件事：等音频特征输入队列有块，
取出一块，交给 Session，等 Session 返回，再取下一块。

它不并发、不并行、不开线程池。任何时刻最多只有一个 Session 在跑，这就是后面
「解码器不用加锁」的全部依据。队列空的时候，线程睡在条件变量上，不占 CPU；主线程
投一块，它就醒一次。

这里说的「唤醒」是条件变量叫醒线程，不是 KWS 的关键词唤醒。两者只是中文词相同，
没有关系。

### ⑦ 处理：Session 决定这块输入用来做什么

后台线程不直接理解音频，它把音频特征输入块交给一个 **Session 类**。Session 是每种
能力的统一入口：

- 单模式用 `AsrSession`，内部调用 `AsrDecoder::accept_features()` 拿到本次新增
  token，再累积成全量历史（`all_ids_`）；解码器自身只保留最近 128 个 token；
- 双模式用 `KwsAsrSession`，内部维护模式机，决定这一步继续监听唤醒词，还是做语音
  识别；
- 将来接 TTS，就写一个 `TtsSession`，内部调用 TTS 引擎；输入块换成 TTS 需要的类型，
  但 `on_block` 这个入口不变。

这就是这次要统一的点：**ASR 不再用 lambda + 外部快照的特例，而是和 KWS、双模式
一样，包成一个 Session 类**。Session 自己持有解码器引用，自己保存结果快照，对外
只暴露 `on_block(输入块)` 和几个读取结果的接口。以后加能力，只需要加一个 Session
类，Worker 和入口装配方式都不变。

Session 内部保存跨块状态——encoder 的状态张量、beam、还没凑满一块的特征尾巴——
所以同一个解码器必须被同一线程、按顺序调用。Worker 的「单线程 + 串行」正好满足
这个条件，解码器内部因此不需要加锁。这不是解码器自己保证的，而是调用方给的契约；
如果入口在别处又直接调了一次 `accept_features()`，这个契约就被破坏了。

### ⑧ 发布：把结果写到快照

Session 处理完一块后，把结果写进一个线程安全的快照。单模式的 `AsrSession` 内部
用 `TextSnapshot`：一把锁加一个字符串，`set()` 写、`get()` 读；双模式的
`KwsAsrSession` 用自己的 一组字段，包括文本、当前模式、最新事件和本段统计。

写快照只在赋值那一瞬间拿锁，不会拿着锁做推理。快照只保留最新值，不排队、不累积：
界面关心的是「现在是什么状态」，不是历史每一个中间结果。快照归 Session 所有，
Worker 不知道它的存在。

### ⑨ 显示：主线程自己读快照

主线程每轮渲染时顺手读一下 Session 的快照：有新文本就更新窗口底部，有模式变化就
更新状态栏；没有新结果就保持上一帧。读的时候只短暂拿一下快照锁，不会等后台解完。

整个流程里，主线程和后台线程唯一的接触点就是「音频特征输入队列」和「快照」这两处，
而且都是短时间的加锁，谁也不会阻塞谁。

### 把这条路径连起来看

前半段（采集、前端、分叉）在主线程，后半段（排队、Session 处理、发布）在后台，
最后通过快照回到主线程显示。主线程从头到尾没有调用过模型，后台线程从头到尾没有
碰过设备和窗口。两边靠一个音频特征输入队列和一个快照连接，职责非常清楚。

## 2. 为什么需要这层框架

### 2.1 如果全放在主线程

最直接的做法是把推理也写在主循环里：取一块音频，算特征，跑 encoder / decoder /
joiner，更新文字，再画图。单看代码很顺，但在 Jetson 上实测，主循环吞吐只有 0.99，
刚好擦着实时。这意味着任何一点额外负载——窗口重绘、日志、系统抖动——都会让主循环
跟不上设备，取流缓冲（2.56 秒）很快被填满，开始丢音频。

音频丢块和视频丢帧不一样。视频丢一帧只是画面卡一下；音频丢块是识别结果里少字，
而且补不回来。所以主线程必须保持轻量，推理不能和取流抢同一个循环。

### 2.2 如果每种能力各写一套线程

把推理挪到后台之后，最初的做法是写一个 ASR 专用 worker：它持有 `AsrDecoder`，
维护自己的音频特征输入队列、锁、条件变量、文本快照和收尾逻辑。这个 worker 能工作，
但它是和 ASR 绑死的。

等到要接 KWS，就得再写一个 KWS worker；将来接 TTS，再写一个 TTS worker。每写一个，
队列、丢最旧、尾块保护、空块过滤、异常处理、排空、join 都要重新实现一遍。这些逻辑
和具体能力无关，却要被复制多次；复制一次就多一次写错的机会，比如忘了尾块阻塞、
忘了异常捕获、忘了析构 join。

### 2.3 框架给出的答案

真正跨能力不变的东西只有两样：**线程和音频特征输入队列**。真正变化的东西也只有两样：
**拿到一块之后做什么**、**结果怎么保存**。

所以框架把它们拆开：`BlockWorker` 只负责线程、队列、背压、尾块、异常和收尾；
「做什么」交给 Session 类的 `on_block`；「结果怎么保存」交给 Session 自己的快照。
这样 ASR、KWS、双模式、将来的 TTS 都复用同一个 Worker，只是换一个 Session。

## 3. 三方的约定

可以把这套框架想成三方在各自表态。这些「表态」不是运行期协商，而是装配时由代码
固定下来的约定，但用它来理解职责很直观。

主线程说：我每一轮能产出一块特征，我把它放进音频特征输入队列；我想要的是最新的文本和
当前模式；但我不会停下来等你算完，因为取流和画面不能断。

Session 说：我拿到一个音频特征输入块，能产出文本、关键词命中或者模式切换；解码器只能我
一个人碰，因为我内部有跨块状态；算完我会把结果写到自己的快照里，谁要谁自己看。

Worker 说：你不用管我什么时候算、算多久。你放进音频特征输入队列的块我按顺序排队；
我一次只放一块进去；我跟不上时丢掉最旧的，保证你看到的是接近当前声音的结果；
收尾那块我绝不丢；你抛异常我兜住，不会让整个进程退出；你要结束时，我先把队列里
的块处理完再退出。

三者对齐之后，主线程和 Session 在稳态下确实互不等待：主线程投递不阻塞，读快照只
拿一下锁；后台线程按自己的速度消费，慢了就丢最旧，不反压主线程。唯一的例外是
收尾：主线程投最后一块时可能短暂等队列腾位置。此时已经不需要保实时，等是安全的。

有一点要修正直觉：Worker 不会「主动把输出送给主线程」。它主动处理的只有输入侧——
从音频特征输入队列取块、调用 Session。输出是 Session 写进快照，主线程想看时自己去读。
所以更准确的说法是：

> 主线程往传送带上放块，Worker 一次取一块喂给 Session，Session 把结果写到白板上，
> 主线程自己看白板。

## 4. 四个角色

主线程是唯一碰设备和界面的线程。它负责取流、前端、语谱图、按键，以及读快照显示。
它不直接调用解码器，也不等待处理结果。这样做的原因很实际：Jetson 上把推理放回
主循环，吞吐只剩 0.99，设备 2.56 秒的取流缓冲很快就会溢出。主线程的职责不是算得
多，而是不要停。

`BlockWorker` 是并发管家。它只做与「块」无关的通用工作：音频特征输入队列、限流、单线程
串行、空块过滤、尾块保护、异常捕获、收尾排空、析构 join。它不知道块里装的是特征
还是 TTS 请求，也不知道 Session 会算出什么。它的价值不在于「开了一个线程」，而在于
把那些容易写错的并发细节集中到一处，只维护一份。

Session 是每种能力的统一入口，包括 `AsrSession`、`KwsAsrSession` 和将来的
`TtsSession`。它持有解码器引用，负责「拿到一块输入做什么」，并保存结果快照。它
不创建线程，也不碰音频特征输入队列；线程和队列是 Worker 的事。把 ASR 也做成 Session，
是为了让所有能力共用同一条装配路径，而不是让 ASR 成为 lambda 的特例。

解码器是 `AsrDecoder` 和 `KwsDecoder`。它们只做算法：特征进去，文本或命中出来。
它们不是线程安全的，也不打算做成线程安全——由 Worker 保证只有一个人调用，比在
每个解码器内部加锁更简单，也更快。

## 5. 两条独立的数据通路

### 5.1 输入通路：主线程推，Worker 拉

```
主线程：push(音频特征输入块) ──► 音频特征输入队列 ──► Worker 取一块 ──► Session.on_block ──► 解码器
```

主线程是生产者，Worker 是唯一消费者。生产快于消费时，队列满，丢最旧；消费快于
生产时，Worker 睡在空队列上。两边都不需要知道对方的速度，也不需要互相通知「我
准备好了」或者「你慢一点」。音频特征输入队列本身就是缓冲和调节器。

### 5.2 输出通路：Session 写，主线程读

```
Session：算出结果 ──► 快照.set(结果) ──锁──► 主线程 快照.get() → 显示
```

Worker 完全不参与这条路。快照只保留最新值，主线程每轮主动读；读不到新值就沿用
上一帧。这样主线程的刷新节奏由它自己决定，不会被后台每处理完一块就打断一次。

### 5.3 为什么必须分开

如果让 Worker 同时管输出，它就必须知道输出是文本、模式还是音频，通用性立刻消失，
又回到「一种能力一个专用 Worker」的老路。分开之后，Worker 只认「块」，输出格式由
Session 自己决定，将来接 TTS 也不用改 Worker。

## 6. 双模式：唤醒 + 识别

```
┌────────────────┐   命中唤醒词     ┌────────────────┐
│   KWS 监听      │ ──────────────► │   ASR 识别      │
│ 只喂 KwsDecoder │  回填最近 1 秒   │ 只喂 AsrDecoder │
└────────────────┘                 └────────────────┘
        ▲                                  │
        └──── 结束语 / 空闲 10 秒 ──────────┘
               两个解码器都 reset
```

双模式解决的是「平时只听几个唤醒词，被叫到之后才做完整识别」的问题。如果一直跑
完整 ASR，计算量大、误识别多；如果只跑 KWS，又没法听懂命令。所以做成两个阶段，
按需切换。

### 6.1 一次唤醒的完整过程

假设用户先说「小智同学」，再说「打开客厅的灯」，最后说「再见」。整个过程大致如下。

最开始处于监听阶段。每一块音频特征输入只交给 `KwsDecoder`，它用关键词前缀树约束
束搜索，只有走完某个关键词的发音序列、并且后面跟了足够的 blank 帧，才算一次命中。
主线程这边看到的只是滚动语谱图和「KWS | listening」的状态，后台在安静地做束搜索。

某个时刻，KWS 命中了「小智同学」。`KwsAsrSession` 先把 `AsrDecoder` 重置，再把
最近 100 帧特征回填给它，然后切到识别模式，并发布一条「唤醒」事件。主线程下一轮
读快照时看到模式变成 ASR，窗口底部的状态文字随之改变。回填的作用是让 ASR 从唤醒
词附近开始听，这样紧接着说出的命令词不会因为切换而丢掉开头。代价是识别文本开头
可能带上唤醒词本身，这是可以接受的。

进入识别阶段后，每一块音频特征输入只交给 `AsrDecoder`。只要它还在产出新 token，就
刷新空闲计时，说明用户还在说话。主线程持续从快照读文本，窗口底部的字一行行增加。

用户说完「打开客厅的灯」后停顿，或者直接说「再见」。如果是结束语，状态机立即
累计本段统计，把两个解码器都重置，切回监听；如果是长时间没有新 token，空闲计时
超过 10 秒，也走同样的切回流程。切回之后，KWS 重新从当前音频开始监听，ASR 的文本
清空，窗口回到「KWS | listening」。

### 6.2 两个边界

第一个边界是回填。回填帧数是 100，大约 1 秒。填得太多，ASR 会把唤醒词前面的无关
内容也听进去；填得太少，命令词开头可能被切掉。100 帧是当前调好的折中值，入口里
把它写成常量，方便调整。

第二个边界是收尾。程序退出时会补 100 帧特征 0 给解码器凑满最后一个 chunk，但这
只对 ASR 有意义。KWS 不能用特征域的 0 当静音——那是 log 能量 1，不是真静音，喂进去
没有意义。所以收尾块带一个 `is_tail` 标记，`KwsAsrSession` 在 KWS 模式下看到它就
直接跳过，ASR 模式下才正常解码。Worker 只负责把标记传下去，不解释它的含义。

## 7. Worker 做什么、不做什么

Worker 做的是一组看起来琐碎、但漏一条就会出问题的并发工作。

它开一个线程，而且只开一个。它维护一条有界的音频特征输入队列，满了丢最旧。它把收尾
块单独走一条阻塞路径，保证最后几个字不被丢。它过滤 0 帧空块，避免空块挤占容量。
它保证 Session 串行执行，让解码器可以不加锁。它捕获 Session 的异常，记录后停止
消费，不让异常穿出线程。收尾时它把已入队的块处理完再退出。析构时它兜底 join，
避免 `std::thread` 在 joinable 状态下析构直接 terminate。

这些工作单独看都不难，难的是每一条都不能漏，而且要和控制流、锁、条件变量配合好。
把它们集中在一个模板里，入口就不用再关心这些细节；如果分散在每个入口里，每接一种
新能力就要重新证明一遍「这次没有漏」。

它不做的事情同样明确。它不做解码，不知道文本、模式、关键词；它不定义输出格式，
不碰快照；它不做排序、优先级、去重；它只保证尾块不丢，普通块在落后时是允许丢的。
这些限制不是能力不足，而是刻意划出的边界：边界越清楚，复用越安全。

最容易被低估的是「串行」这一条。它不是实现细节，而是解码器敢不加锁的前提。很多
人会觉得「我只创建了一个线程，所以当然是串行的」——但如果入口在别处又直接调了一次
`accept_features()`，或者以后有人为了性能把 Session 改成线程池，这个前提就没了，
解码器会在没有任何报错的情况下慢慢算错。文档把这条写成不变量，就是为了让后来的人
知道它不能随便动。

## 8. 六条关键约定

**一、一个 Worker 一个线程。** Session 不会并发执行，同一个解码器也不会被两个线程
同时碰到。需要并行处理两种能力时，不要共享解码器；要么在 Session 内部按顺序分发，
要么各自持有独立的解码器。

**二、普通块满时丢最旧。** 丢的是过时的输入，不是音频；目的是让界面贴近当前声音，
而不是无限囤积。丢的块数会进统计，便于判断后台是否跟得上。如果丢弃持续增长，说明
处理速度不够，应该先查模型和执行器，而不是加大队列。

**三、尾块绝不丢。** 收尾块走单独的阻塞入口，满了就等消费者腾位置。它承载的是最后
几个字，丢了无法补回；此时主循环已经退出，等待不影响实时性。调用顺序必须是先投
尾块，再结束 Worker；反过来的话，尾块会被当成「已经结束」直接丢掉。

**四、空块不入队。** 0 帧块没有新特征，未凑满一帧的样本还在前端缓存里，跳过它不会
丢音频，却能避免无效块挤占队列。判断空块的条件是 `n_frames <= 0` 或者数据为空，
这个判断在投递方完成，Worker 不关心特征的含义。

**五、持锁不解码。** Worker 解锁之后才调用 `on_block`；Session 只在小段赋值时拿
快照锁。两条都遵守，两把锁就不会嵌套，也就不会死锁，主线程也不会被推理拖住。这条
约定看起来像性能优化，实际上是正确性问题：一旦有人拿着队列锁去解码，主线程的每
一次投递都会等整个推理结束，实时性就没了。

**六、先 join 后销毁。** Worker 要声明在所有被它引用的对象之后。C++ 按声明逆序
析构，这样 Worker 先停线程，Session、解码器和快照后销毁，不会出现「线程还在跑、
对象已经没了」的未定义行为。这个错误在测试里不一定立刻暴露，但一旦触发就是随机
崩溃，所以要在装配代码里用声明顺序保证，而不是靠运气。

## 9. 统一输入：每个能力一个 Session

这一节解释为什么 ASR 也要从「lambda 特例」改成 Session 类。

### 9.1 之前的两种写法不一致

在此之前，单模式 ASR 的接法是：

```cpp
TextSnapshot asr_text;
BlockWorker<LogfbankFeatures> worker(
    [&decoder, &asr_text](const Item& item) {
        asr_text.set(decoder.accept_features(item.block));
    });
```

双模式 KWS 的接法是：

```cpp
KwsAsrSession session(asr, kws, ...);
BlockWorker<LogfbankFeatures> worker(
    [&session](const Item& item) { session.on_block(item); });
```

一个把逻辑摊在 lambda 里、快照放在外面；另一个收进类里、快照放在内部。两种写法都
能工作，但入口的装配方式不一致：以后每加一种能力，都要重新决定「逻辑放 lambda 还是
放类」「快照放外面还是放里面」。能力越多，风格越散。

### 9.2 统一成 Session 类

现在把每种能力都统一成 Session 类，约定两个接口：

```cpp
class XxxSession {
public:
    void on_block(const AudioFeatureInput& input);   // 处理一个音频特征输入块
    // 以及若干读取结果的接口，比如 latest_text() / mode() / latest_event()
};
```

其中 `AudioFeatureInput` 就是音频特征输入队列里的一项：

```cpp
using AudioFeatureInput = BlockWorker<LogfbankFeatures>::Item;
// { LogfbankFeatures block; bool is_tail; }
```

单模式 `AsrSession` 的实际形态（已落地）：

```cpp
class AsrSession {
public:
    AsrSession(AsrDecoder& decoder, AsrSessionConfig cfg);  // 分段长度 + txt 路径
    void on_block(const AudioFeatureInput& input);          // Worker 线程
    void settle_segment();                                  // 立即结算当前段（双模式切回用）
    std::string latest_text() const;                        // 显示快照
    std::string finish();                                   // join 后结算尾段
    // all_token_ids() / n_segments() / transcript_ok() ...
};
```

`on_block()` 做四件事：取增量 token → 并进全量与当前段 → 满 64 个结算并写
`log/asr_last_text.txt` → 刷新显示快照。它不碰线程、队列，也不直接调用
`run_encoder` / `run_joiner`。

入口的装配方式对所有能力都一样：

```cpp
AsrSessionConfig cfg;
cfg.transcript_path = join_path(project_dir, "log/asr_last_text.txt");
AsrSession session(decoder, cfg);
BlockWorker<LogFbankFeatures> worker(
    [&session](const AudioFeatureInput& input) { session.on_block(input); },
    [](const LogFbankFeatures& f) {
        return f.n_frames <= 0 || f.data.empty();
    },
    50);
```

双模式只是把 `AsrSession` 换成 `KwsAsrSession`，Worker、队列、投递、收尾都不变。

### 9.3 这样做的收益

第一，**扩展路径统一**。以后接 TTS，只需要写一个 `TtsSession`，实现 `on_block` 和
自己的快照读取接口，入口的装配代码形状不变。不需要再判断「这个能力要不要包类」。

第二，**状态归属清楚**。结果快照、模式、统计都归 Session，Worker 只碰输入。谁写
谁读、锁在哪，都跟着能力走。

第三，**输入格式可以统一**。音频类能力共用 `AudioFeatureInput`（特征块 + 收尾标记）；
如果某个新能力需要的不是音频，就定义自己的输入类型，比如 `TtsInput`，但「队列 +
`on_block` + 快照」这套模式不变。统一的是接口形状，不是强行让所有能力用同一种
数据。

第四，**测试和复用更容易**。Session 不依赖线程和队列，可以单独构造、单独喂块、
单独检查快照；Worker 也不依赖具体能力，可以单独测背压和收尾。

### 9.4 不强行统一的部分

Session 的输入类型不要求全部相同。ASR 和 KWS 吃 `AudioFeatureInput`，TTS 可能吃
`TtsInput`；它们共享的是 `on_block` 这个入口形状和 Worker 的并发策略，不是同一个
具体类型。把「统一」理解成「同一套装配模式」，而不是「所有能力必须用同一个数据结构」，
扩展时会更灵活。

## 10. 接一种新能力要做什么

现在流程固定为三步：定义输入块（如果需要新类型）、写一个 Session 类、用同一个
Worker 装配。

比如将来接 TTS：

```cpp
using TtsInput = BlockWorker<TtsRequest>::Item;

class TtsSession {
public:
    explicit TtsSession(TtsEngine& engine) : engine_(engine) {}
    void on_block(const TtsInput& input) {
        // 合成音频，结果写进自己的快照或输出队列
    }
    // 读取结果的接口
private:
    TtsEngine& engine_;
};

TtsSession session(engine);
BlockWorker<TtsRequest> worker(
    [&session](const TtsInput& input) { session.on_block(input); },
    [](const TtsRequest& r) { return r.text.empty(); });
```

不需要再写 `TtsWorker`，不需要再复制一遍音频特征输入队列、锁、条件变量、丢最旧、尾块、
异常和 join。只要「一块一块处理、落后时可以丢旧」这个形态合适，就复用同一个 Worker。

如果 TTS 需要「一块都不许丢」或者不同的背压策略，那也应该在 Worker 里增加一个
策略参数，而不是复制整个类。复用不等于所有场景都用同一种策略；把变化点收敛到
一个参数，比让每个入口各写一套更容易维护。

## 11. 常见误解

**「Worker 就是开个线程。」** 开线程只是它做的第一件事。真正容易写错的是音频特征
输入队列的上限、丢最旧、尾块阻塞、空块过滤、异常退出、排空和 join；这些才是它存在的
理由。如果只需要一个线程，`std::thread` 就够了；之所以要 Worker，是因为不想在每个
入口重写一遍这些细节。

**「输出是 Worker 送回主线程的。」** 不是。Worker 只处理输入侧；输出是 Session 写
快照，主线程主动读。Worker 连输出是什么类型都不知道。这个区别很重要：它意味着新增
一种输出格式不需要改 Worker，只需要换一个 Session。

**「算法是另一个并行线程，所以主线程和算法互不等待。」** 算法没有自己的线程，
`on_block` 同步跑在 Worker 线程上。主线程不等它，是因为投递不阻塞、读快照只拿一下
锁，而不是因为算法在别处并行运行。理解这一点，才能正确判断「处理慢」会带来什么
后果：不是主线程卡住，而是队列丢块、结果变旧。

**「文档里的唤醒是唤醒词。」** 不是。这里的「唤醒」指条件变量叫醒睡眠中的线程：
音频特征输入队列空时 Worker 睡着，主线程投一块就把它叫醒。和 KWS 的关键词唤醒没有关系。
文档里同时出现这两个词时，看上下文就能区分。

**「单模式没必要包类。」** 从「只做一个 ASR」看确实没必要；但从「以后还要加能力」
看，包类是为了统一装配路径，而不是为了眼前这点逻辑。ASR 包成 `AsrSession` 之后，
它和 `KwsAsrSession`、将来的 `TtsSession` 就站在同一条扩展线上，入口不需要为每种
能力写不同的接法。

## 12. 落地方式

`BlockWorker` 放在 `audio_ai_process/block_worker.h`，是一个 header-only 模板，
随 `lib_audio_ai_process` 安装，不新增 `.cpp`，也不引入新的外部依赖。

单模式的 `test_mic_asr.cpp` 用它替换原来的 `AsrWorker`：Worker 负责线程和音频特征
输入队列，`AsrSession` 负责调用 `AsrDecoder`、保存文本快照。双模式的
`test_mic_kws_asr.cpp` 用同一个 Worker，Session 换成 `KwsAsrSession`，由它维护模式机、
回填环、事件和统计。

迁移前后行为不变：队列上限 50、满时丢最旧、尾块阻塞、空块跳过、异常记录、排空
退出全部保留。变化的只是把「线程 + 队列」从 ASR 专用的 `AsrWorker` 里抽出来，
变成任何能力都能复用的 `BlockWorker`，并把单模式的 lambda 收进 `AsrSession`。

迁移分两步：先做纯重构（Worker + AsrSession，行为不变），再做双模式入口。第一步
已完成：`test_mic_asr.cpp` 的输出文本、后台丢弃统计、尾块处理与改造前一致，另增加
按 64 token 分段落盘。若第二步在真机上出问题，可以单独保留这一步。

一句话总结：

> **Worker 是输入侧的并发管家：它把主线程投递的音频特征输入块排队、限流、串行地喂给
> Session，并在收尾时保证队列排空；Session 把结果写到快照，主线程自己读。它不做
> 算法、不送结果、不解释语义，只保证并发边界。**
