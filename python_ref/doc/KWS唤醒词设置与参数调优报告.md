# KWS 唤醒词设置与参数调优报告

> 记录从「模型自带的 10 条测试词」换成「正式唤醒词」的完整过程：缺口分析、
> 工具实现、两轮真机录制（15 条 + 30 条）、参数扫描，以及最后的选词建议。
>
> 涉及代码：`tools/gen_keywords.py`、`tools/record_keywords.py`、
> `tools/eval_keywords.py`、`src/kws_decode.py`、`test_mic_kws_asr.py`
>
> 基础原理见 [KWS 调研报告](sherpa-onnx-KWS关键词唤醒调研报告.md)。

---

## 一、结论先行

1. **阈值从来不是瓶颈**。两轮录音（15 条 + 30 条）里，未命中全部是
   「没走到关键词末端」，没有一条被 `ac_threshold` 挡住（score=2.0 时例外，
   见第 3 条）。
2. **束宽竞争被排除**。三个词拆成单关键词逐个测，命中率和共存时完全一致；
   逐词参数落地后三词共存仍是 27/30，与统一参数一致。
3. **score 和 threshold 互相抵消**。加分拉回的命中 `avg_prob` 天然偏低，
   提高防误触门槛又会把它们挡回去。score=2.0 时直接有 3 条被阈值挡回。
4. **推荐逐词配置**（30 条实测 27/30）：

   | 关键词 | score | threshold | 命中 |
   |---|---|---|---|
   | 小智同学 | 1.5 | 0.30 | 9/10 |
   | 小智小智 | 1.5 | 0.30 | 8/10 |
   | 你好小智 | 1.0 | 0.35 | 10/10 |

   统一参数的最佳点是 `score=1.5, threshold=0.30`（同样 27/30）。
   逐词配置的价值在于「你好小智」本来就全中，可以单用 0.35 的阈值，
   留出更多防误触余量。
5. **「你好小智」召回最稳，但误触风险最高** —— 「你好」是日常高频词，
   而另外两条以「小智」开头，误触面小得多。只凭召回率选它是不完整的判断。
6. **score=2.0 是反效果**：`avg_prob` 被压到 0.225~0.238，命中率反而回落。
7. **小智小智到顶了**：score=1.5 下仍漏 2 条，卡在声学层面；继续加分
   只会把别的词一起压低，救不回来。

## 二、问题的起点：现状与缺口

改造前的状态：

| 项 | 现状 | 问题 |
|---|---|---|
| `keywords/kws_keywords.txt` | 模型自带的 10 条测试词 | 不是正式唤醒词 |
| 生成工具 | 不存在 | 换词只能手工抄 token，易错 |
| `pypinyin` | 未安装 | `text2token` 跑不起来 |
| 参数观测 | 无 | 命中时不打印 `avg_prob`，未命中时什么都不打印 |

最后一项是真正的短板：**调阈值最需要的数据恰恰是「差一点」的分数**，
而改造前的实现把它们全部静默丢掉了。

## 三、实现：三层结构

### 3.1 文件分工

```
keywords/kws_keywords_raw.txt     人写：一行一个唤醒词，可带 :score #threshold
        │
        │  tools/gen_keywords.py
        │      text2token(phone+ppinyin) → pypinyin 注音 / en.phone CMU 词典
        ▼
keywords/kws_keywords.txt         生成物：识别侧唯一消费者是
                                  src/kws_decode.py: _load_keywords()
```

`kws_keywords.txt` 变成**生成物而非手写物**，与模型换词时的返工隔离。

### 3.2 生成工具

`tools/gen_keywords.py` 的核心设计是**逐条调用 `text2token`**，不是批量。

原因：`sherpa_onnx.utils.text2token` 对转写失败的词是 `continue`
（`sherpa_onnx/utils.py:133` 的非 CJK 跳过、`:173` 的词表 OOV 跳过），
**返回值长度可能小于输入条数**。批量传会让关键词和 token 行静默错位。

其它校验：

- 转写结果为空 → 报错并指出 raw 行号
- 生成的 token 不在 `tokens.txt` → 报错
- 拒绝 `:0` / `#0`（会被识别侧当成「未设置」而回落全局默认）
- 写盘后用真正的 `_load_keywords` 回读自检

### 3.3 观测点

`src/kws_decode.py` 新增 `debug` 开关，只在一种情况记录：

> **trie 已走到关键词末端，但 `avg_prob < ac_threshold`**

这是命中时拿不到的那批「差一点」的分数，也是唯一能用来定阈值的依据。
去重键是 `(关键词原文, avg_prob)`，同一句话 trie 不前进、分数不变，
所以一句话只产生一条记录。

另外新增 `best_trie_level` 属性 —— 记录最佳假设在 trie 上走到的深度，
用于诊断「未命中是开头没对上，还是只差最后一个音」。

`test_mic_kws_asr.py` 配套改动：`KWS_DEBUG = True`、命中时打印 `avg_prob`、
退出时汇总被挡住的候选。

## 四、两个参数的完整链路

关键词文件里那两个可选的 `:1.2` 和 `#0.35` 是最容易含糊过去的地方。
这一节把「它是什么、谁读、怎么传到束搜索、不写会怎样」逐层拆开
（下面的 1.2 / 0.35 只是语法示例，实际取值见第七节）。

### 4.1 一行关键词文件长什么样

```
x iǎo zh ì t óng x ué :1.2 #0.35 @小智同学
└──────── token 序列 ────────┘ └──┘ └───┘ └────┘
                              加分  阈值   原文
```

`_load_keywords` 按每个 word 的**首字符**分流：

| 首字符 | 字段 | 是否必须 | 缺省行为 |
|---|---|---|---|
| 能在 `tokens.txt` 查到 | token | 至少一个 | — |
| `:` | boosting score（关键词加分） | 否 | 用全局 `keywords_score` |
| `#` | 触发阈值（ac_threshold） | 否 | 用全局 `keywords_threshold` |
| `@` | 原文（打印 / 结果里显示） | 否 | 用 token 拼接 |

三个参数**可以任意组合出现**，顺序也不敏感。

### 4.2 谁读取这个文件

只有一处，进入时读一次：

```
test_mic_kws_asr.py:216   KWS_KEYWORDS_TXT = .../keywords/kws_keywords.txt
        ↓ 作为构造参数传入
KeywordSpotter.__init__()
        ↓
KeywordSpotter._load_keywords(path, token2id)      ← 唯一的读取方
        ↓ 返回 4 个平行列表
(ids, scores, phrases, thresholds)
        ↓
_ContextGraph(token_ids, 全局score, 全局threshold,
              scores, phrases, thresholds)
```

生成工具和识别侧之间**没有代码契约**，只通过这份文本文件交接。
`gen_keywords.py` 输出格式对，识别侧不关心它怎么来的。

### 4.3 参数怎么进到束搜索

分三步，**参数在构造期就编进 trie 节点了，不是每帧查文件**。

**第 1 步：解析成平行列表**

每条关键词攒出四个值：

```python
ids_all.append(token_ids)         # [71, 182, ...]
scores_all.append(score)          # :1.2 → 1.2，没写就是 0.0
phrases_all.append(phrase)        # @小智同学 → 小智同学
thresholds_all.append(threshold)  # #0.35 → 0.35，没写就是 0.0
```

**第 2 步：编译进 trie 节点**

`_ContextGraph._build` 把每条关键词插进前缀树，**分数摊到每个 token 节点上**：

```python
node_score=node.node_score + score,                    # 每走一步累加
output_score=(node.node_score + score) if is_last else 0.0,
ac_threshold=ac_thr if is_last else 0.0,               # 只有末节点带阈值
```

以 `:1.2 #0.35` 的「小智同学」为例：

```
root
 └─ x       node_score=1.2
     └─ iǎo  node_score=2.4
         └─ zh  node_score=3.6
             └─ ì   node_score=4.8
                 └─ t   node_score=6.0
                     └─ óng  node_score=7.2
                         └─ x  node_score=8.4
                             └─ ué  node_score=9.6
                                    is_end=True
                                    output_score=9.6
                                    ac_threshold=0.35   ← #0.35 落在这
```

**加分是按 token 计的，不是按关键词计的**：8 个 token 走完，总分 8 × 1.2 = 9.6。

**第 3 步：每帧两个通道各取所需**

**加分通道** —— 束搜索每扩展一个非 blank token，走一步 trie，把**增量分**
加到 `log_prob`：

```python
context_score, new_state, _ = self._graph.forward_one_step(...)
new_hyp.log_prob = float(flat[flat_idx]) + context_score    # :743
```

返回的是「新节点 node_score − 旧节点 node_score」，也就是这一步的边分。
它只影响**排序** —— 谁更容易被留在束里。

**阈值通道** —— trie 走到末端后，在触发判定时读末节点的 `ac_threshold`：

```python
avg_prob = mean(best.ys_probs[:level])
if best.num_trailing_blanks > 1 and avg_prob >= matched_state.ac_threshold:  # :758
```

`avg_prob` 是**纯声学概率**的平均（`ys_probs[i]` 来自 `logprobs` 的 exp，
不含任何加分），所以两条通道互不干扰：

| | `:score` | `#threshold` |
|---|---|---|
| 卡在哪 | 束搜索排序时 | 触发判定时 |
| 作用对象 | `log_prob`（含加分的累计分） | `avg_prob`（纯声学概率） |
| 调大 | 更容易**走到**关键词 | 更**难认**这个关键词 |
| 默认 | 1.0 | 0.25 |
| 典型用途 | 说了不认（被淹没） | 没说也认（误触） |

### 4.4 不写参数时发生什么

参数是可选的。以早期版本的 `kws_keywords.txt` 为例，三行都没有 `:x` / `#x`，
解析结果是 `scores=[0.0, 0.0, 0.0]`、`thresholds=[0.0, 0.0, 0.0]`，
然后 `_build` 里回落：

```python
score = scores[i] if scores else 0.0
if score == 0.0:
    score = self.context_score            # 全局 keywords_score
ac_thr = ac_thresholds[i] if ac_thresholds else 0.0
if ac_thr == 0.0:
    ac_thr = self.ac_threshold            # 全局 keywords_threshold
```

全局默认值是 **1.0 / 0.25**，定义在 `KeywordSpotter.__init__` 的默认参数上。

当前落地的逐词参数（第六节实测得出）：

```
x iǎo zh ì t óng x ué :1.5 #0.3 @小智同学
x iǎo zh ì x iǎo zh ì :1.5 #0.3 @小智小智
n ǐ h ǎo x iǎo zh ì :1 #0.35 @你好小智
```

**注意一个坑**：`0.0` 是「未设置」的哨兵值，所以 `#0.0` 不等于「怎么都触发」，
而是「用全局默认」。想要必中只能写个极小正数。生成工具因此直接拒绝 `:0` / `#0`。

### 4.5 官方例子里的阈值为什么差别大

`Keyword_spotting_index.rst` 里那三行：

```
小爱同学 :2.0 #0.6
你好问问 :3.5
小艺小艺 #0.6
```

**那是语法演示，不是调优结论。** 它想表达的是「四个字段可以任意组合出现」，
所以每种组合演一遍：

| 行 | score | threshold | 缺什么 |
|---|---|---|---|
| 小爱同学 | 2.0 | 0.6 | — |
| 你好问问 | 3.5 | **无** | 回落 0.25 |
| 小艺小艺 | **无** | 0.6 | 回落 1.0 |

三个值彼此之间没有可推导的关系：「小爱同学」和「小艺小艺」都以「小」开头、
都是 4 字，阈值却一个 0.6 一个没写。作者没有在做对比实验。

**不要把 0.6 / 0.35 当推荐值抄。**

### 4.6 阈值该怎么定

`avg_prob` 是关键词**每个 token** 在各自输出帧上的声学概率的**算术平均**。
它受三个因素影响：

1. **token 数** —— token 少，平均值方差大，偶然冲高的概率更高；
2. **音素稳定性** —— 鼻音韵母、轻声、连读在快速口语下概率会掉；
3. **说话人与环境** —— 麦克风、噪声、语速。

所以「每个词一个值」在原理上是对的，但**值必须从自己的数据里量出来**。

流程：

```
① 全部用默认，先跑通
② 打开观测（KWS_DEBUG），收集「被阈值挡住」的分数
③ 正样本：说每个唤醒词 10 遍以上，记录命中时的 avg_prob
④ 负样本：说相似音 / 日常对话，记录「trie 已匹配但没过阈值」的 avg_prob
⑤ 阈值定在 正样本最小值 与 负样本最大值 的中点，偏向正样本一侧
```

两轮实测（详见第六节）：

- score=1.0 时，阈值从 0.25 提到 **0.35 是零召回损失**的（最低命中 0.362）；
- score 越高，能守住的阈值上限越低：1.2 只能到 0.30，1.5 到 0.30，
  再高就开始把加分拉回的命中挡回去。

负样本尚未采集，所以这些值只是「不亏召回」，还不是「最优阈值」。

## 六、参数调试

### 6.1 两轮样本

**第一轮（15 条，每词 5 遍）**：录制脚本的方式是「检测到起音后录固定 2 秒」。
但按回车到真正开口之间有 0.5~1.2 秒反应时间，也被算进了窗口，慢语速的句子
尾巴会被硬切。事后核对能量：小智同学 9/10 条、小智小智 5/10 条的
「尾部能量 / 整体能量」超过 0.5，说明录到结尾时人还在说话 —— 这一批的
未命中很大一部分是录音造成的，不能直接拿来定参数。

**第二轮（30 条，每词 10 遍）**：脚本改成「说完按回车停」（`REC_STOP_PAD`
0.4 秒尾巴，连续静音 2 秒兜底）。本节结论以第二轮为准。

### 6.2 第一轮结果（15 条，仅存档）

| score | threshold | 你好小智 | 小智同学 | 小智小智 | 合计 |
|---|---|---|---|---|---|
| 1.0 | 0.25 | 5/5 | 3/5 | 2/5 | 10/15 |
| 1.0 | 0.35 | 5/5 | 3/5 | 2/5 | 10/15 |
| 1.0 | 0.45 | 4/5 | 2/5 | 2/5 | 8/15 |
| 1.5 | 0.25 | 5/5 | 3/5 | 4/5 | 12/15 |
| 1.5 | 0.40 | 4/5 | 2/5 | 3/5 | 9/15 |
| 1.2 | 0.35 | 4/5 | 3/5 | 3/5 | 10/15 |
| 1.2 | 0.40 | 4/5 | 2/5 | 2/5 | 8/15 |

当时得出两个结论：阈值不是瓶颈（零条被挡），以及 score 加分拉回的命中
`avg_prob` 偏低（1.5 时小智小智只有 0.322~0.485）。这两点第二轮都复现了。

### 6.3 第二轮结果（30 条）

| score | threshold | 你好小智 | 小智同学 | 小智小智 | 合计 |
|---|---|---|---|---|---|
| 1.0 | 0.25 | 10/10 | 8/10 | 6/10 | 24/30 |
| 1.0 | 0.35 | 10/10 | 8/10 | 6/10 | 24/30 |
| 1.2 | 0.30 | 10/10 | 8/10 | 7/10 | 25/30 |
| 1.2 | 0.35 | 10/10 | 7/10 | 6/10 | 23/30 |
| 1.5 | 0.30 | 10/10 | 9/10 | 8/10 | **27/30** |
| 1.5 | 0.35 | 10/10 | 8/10 | 7/10 | 25/30 |
| 2.0 | 0.25 | 10/10 | 7/10 | 7/10 | 24/30（3 条被阈值挡住） |
| **逐词** | 1.5/0.30 + 1.0/0.35 | 10/10 | 9/10 | 8/10 | **27/30** |

完整命中率与 `avg_prob`（逐词配置）：

| 关键词 | 命中 | 命中时 avg_prob (min/mean/max) |
|---|---|---|
| 小智同学 | 9/10 | 0.345 / 0.504 / 0.589 |
| 小智小智 | 8/10 | 0.304 / 0.445 / 0.545 |
| 你好小智 | 10/10 | 0.362 / 0.531 / 0.654 |

### 6.4 三个发现

**① 阈值不是瓶颈**

第二轮 30 条里所有未命中仍然是「没走到关键词末端」，**没有一条被阈值挡住**。
唯一的反例是 score=2.0：加分把 `avg_prob` 压到 0.225~0.238，有 3 条
走到了末端却被 0.25 的阈值挡回去 —— 这正好说明加分和阈值在互相拆台。

**② 束宽竞争被排除**

第一轮把三个词拆成单关键词逐个测（`--keywords` 指向临时文件），命中率与
三词共存时完全一致。第二轮把参数改成逐词配置后，三词共存仍是 27/30，
与统一 `score=1.5, threshold=0.30` 完全相同：共享前缀 `x iǎo zh ì`
没有挤占 `max_active_paths=4` 的束宽，`你好小智` 单独用 0.35 的阈值
也没被另外两个词的高分抢走。

**③ score 和 threshold 互相抵消**

score 提到 1.5 能把小智小智从 6/10 拉到 8/10，代价是命中样本的
`avg_prob` 整体下移：

| 配置 | 小智小智命中时 avg_prob (min/mean/max) |
|---|---|
| score=1.0 | 0.431 / 0.513 / 0.607 |
| score=1.5 | 0.304 / 0.445 / 0.545 |

这时阈值只能守在 0.30；提到 0.35，小智小智掉回 7/10、小智同学掉回 8/10。
**靠加分拉回的命中质量天然偏低，与「提高防误触门槛」直接冲突。**

### 6.5 未命中诊断

用 `best_trie_level` 看未命中样本在 trie 上走到第几个 token（关键词共 8 个）：

| 词 | 样本 | 最远走到 | 说明 |
|---|---|---|---|
| 小智同学 | 04 | 第 1 个 | 开头就没对上 |
| 小智小智 | 04 | 第 4 个 | 第一遍「小智」对上，第二遍断 |
| 小智小智 | 06 | 第 4 个 | 同上 |

对比第一轮，卡的位置从「分散在开头/中间/结尾」收敛到只剩两个位置。
小智小智的两条都卡在第 4 个 token，是叠词被压缩的典型表现（两遍相同音节，
第二遍说得更快更轻），不是随机噪声，也不是参数能救的。

## 七、建议

### 7.1 参数

落地的配置：

```
小智同学 :1.5 #0.30
小智小智 :1.5 #0.30
你好小智 :1.0 #0.35
```

- 「你好小智」本来就 10/10，score 保持默认 1.0，阈值拉到 0.35 留防误触余量；
- 另外两条靠 1.5 的加分把束搜索路径拉回来，阈值守在 0.30；
- **不要用 score=2.0**：`avg_prob` 被压到 0.225~0.238，有 3 条走到末端
  又被阈值挡回，命中率反而下降。

这些值写进 `keywords/kws_keywords_raw.txt`，由 `gen_keywords.py` 生成；
以后调参只改 raw、重跑生成工具，不用动解码代码。

### 7.2 词

1. **小智小智到顶了**：30 条里 8/10，剩下两条都卡在第 4 个 token。
   叠词在这个模型上就是吃亏（两遍相同音节，第二遍被压缩），
   继续加 score 只会把另外两个词一起压低。如果后续负样本显示误触率
   不理想，优先换掉它。
2. 小智同学 9/10，唯一漏的 04 号开头就没对上，属于单条录音问题，
   复测可以确认。

### 7.3 只留「你好小智」是不是最稳

**召回维度：是。** 10/10，`avg_prob` 分布 0.362~0.654 也是三者中最宽裕的。

**但不能只看召回。** 三个词里只有它以「你好」开头：

| 词 | 起始音 | 召回 | 误触风险（未验证） |
|---|---|---|---|
| 你好小智 | `n ǐ h ǎo` | 10/10 | **高** —— 「你好」是日常高频词 |
| 小智同学 | `x iǎo zh ì` | 9/10 | 低 —— 「小智」不是常用词 |
| 小智小智 | `x iǎo zh ì` | 8/10 | 低 |

唤醒词的误触代价通常高于漏检代价：漏检用户会重说一遍，误触会打断正常对话。
现在**没有任何负样本**，这个维度完全是空白。

**结论**：如果只留一个，现阶段「你好小智」的召回数据最好看，但需要先录一组
负样本（说「你好」不接「小智」、日常对话里出现「你好」）验证误触率，
再和「小智同学」比较。
